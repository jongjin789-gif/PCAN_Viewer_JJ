# ECM 조향 MCU / 유저패널 로그 비교 — 2026-09-30

분석 대상: `dist/Panel/JJPKG_HL Mando_ECM_STEER_260930_corrected.pjjupkg`, `Log/CAN_Log_20260930_183540_ECM조향 부팅.trc`, `Log/CAN_Log_20260930_184210_ECM조향 부팅 명령USER.trc`.
사용자 확인: BUS1/BUS2는 별도 ECU이며, 유저패널은 main.py로 실행했다. 원본 패키지·로그·프로그램 코드는 이 분석에서 변경하지 않았다.

**판단:** 이 기록에서는 INIT 명령 불일치나 CRC 오류보다 **10ms 주기 미달 및 큰 목표각 변화**가 우선 조사 대상이다. ECU의 내부 실패 원인을 확정할 DTC/허용 주기·각도 변화율 사양은 없다. 유저패널이 처음부터 계속 동작하지 않은 기록은 아니며, 정상 추종 구간과 추종하지 않는 구간이 모두 존재한다.

**1. 초기화 요청/응답**

두 로그, 두 BUS 모두 아래 요청과 정상 응답을 확인했다. 사용자 설명의 XX 위치는 실제 응답에서 CC이며 패키지의 비교 마스크가 해당 위치를 제외한다. 기록 내 0x71D에서 부정 응답은 발견하지 않았다.

| 단계 | 0x715 요청 | 0x71D 응답 | 패키지 비교 바이트 |
|---|---|---|---|
| 1 | 02 10 60 00 00 00 00 00 | 06 50 60 00 32 00 C8 CC | 0~6 |
| 2 | 05 2F FE F1 03 01 00 00 | 05 6F FE F1 03 01 CC CC | 0~5 |
| 3 | 05 2F FE F6 03 01 00 00 | 05 6F FE F6 03 01 CC CC | 0~5 |
| 4 | 02 3E 00 00 00 00 00 00 | 02 7E 00 CC CC CC CC CC | 0~2 |

각 시퀀스의 RCV 제한은 1000ms, 응답 후 DEL은 100ms다. USER의 요청→응답 지연은 BUS1 약 10~30ms, BUS2 약 20~40ms로 기록된다. 응답 내용을 보면 RCV 조건에 부합한다. BRS는 현재 TRC 형식에 기록되지 않아 로그만으로 조건 일치를 전부 검증할 수는 없다.

근거: MCU 로그 618~820행, USER 로그 4424~4647행(BUS1), 27832~28095행(BUS2). 전체 진단 프레임과 시각은 `metrics.json`에 기록했다.

**2. CRC / AliveCount / Motorola 데이터**

- CRC: polynomial 0x1021, init 0xFFFF, xorout 0, 비반사, 데이터 byte 2~31의 30바이트, 추가 데이터 없음, 결과 MSB→LSB(byte 0~1).
- Python 표준 라이브러리 `binascii.crc_hqx`로 독립 계산해 MCU 7,081개 및 USER 16,866개의 0x163 프레임 모두 일치했다. 현재 패키지의 CRC 설정도 같은 값이다. CRC 바이트 순서나 임의 XOR 변경을 권하지 않는다.
- USER AliveCount는 byte 2이며 BUS1 9,778회, BUS2 7,086회 연속 전이 모두 `(다음-이전) mod 256 == 1`이다. 기록 구간 내 중복/건너뛰기는 없다.
- MCU BUS1에는 활성화 전 약 2초·4초에 201→1 재시작이 두 번 있다. MCU BUS2 및 USER의 연속 카운트 패턴과 구분해야 하며, 이를 근거로 상한을 201로 바꿀 수는 없다.
- USER 첫 카운트는 BUS1 E0, BUS2 BA이며 MCU는 각각 01이다. 단, 카운트 시작값이 반드시 01이어야 한다는 사양은 제공되지 않았다. 현재 코드는 STOP/START만으로 런타임 카운트를 초기화하지 않을 수 있다. 패키지 파일의 초기값과 시험 중 런타임 값은 구분해야 한다.
- 패키지/SYM의 조향 신호는 Motorola start=71, length=16, scale=0.0625, offset=-780. 즉 byte 8~9를 big-endian으로 읽어 `raw*0.0625-780`이며 30 C0는 0이다. 조향 Enable은 byte 3 상위 2비트이고 40이면 1이다. USER BUS1 최초 1개만 Enable=0, 이후 전부 1이며 BUS2는 처음부터 전부 1이다.

**3. 송신 주기 차이**

| 송신원 / 채널 | 0x163 프레임 수 | 중앙 간격 | 99백분위 | 최대 간격 | 관측 송신률(약) |
|---|---:|---:|---:|---:|---:|
| MCU BUS1 | 3,856 | 10.000ms | 15.519ms | 25.311ms | 100/s |
| MCU BUS2 | 3,225 | 10.000ms | 10.098ms | 10.200ms | 100/s |
| USER BUS1 | 9,779 | 20.000ms | 44.850ms | 648.491ms | 46.7/s |
| USER BUS2 | 7,087 | 20.000ms | 40.219ms | 649.147ms | 44.6/s |

패키지 설정은 두 채널 모두 10ms지만 로그의 평균 빈도는 약 절반이다. USER BUS1은 처음 60초 구간 평균 18.02ms, 120~180초 23.68ms, 180초 이후 24.74ms로 악화한다. BUS2도 후반 평균 24.47ms다.

두 BUS 모두 기록 196.264863초 이후 약 649ms 공백이 있다. USER 95516행(BUS1), 95519행(BUS2). 별도 ECU에서 동시에 나타나므로 공통 PC 송신 처리 지연을 우선 의심한다. 이 큰 공백은 앞서 나타난 추종 불량보다 늦으므로 모든 불량의 최초 원인이라고 단정하지 않는다.

코드에서 유저패널의 패킷 타이머는 GUI 스레드의 `QTimer(self)`이고 같은 경로에서 카운트·CRC 계산, bus.send 및 기록을 수행한다. 화면/로그/설정 저장과 송신이 같은 이벤트 루프에 있으므로 그 작업들의 지연이 송신 시점을 늦출 수 있다. 다만 어느 작업이 주요 원인인지는 실행 중 프로파일링이 필요하다. CRC **값**은 정상이며 CRC **처리 비용**은 별도 문제다.

기록상 주의: Tx는 `bus.send` 이후 PC 시각, Rx는 드라이버 시각을 정규화해 기록한다. 기록기는 전체 BUS의 시간을 단조 증가하도록 보정하므로 동일 타임스탬프와 0ms 간격이 생길 수 있다. 이 파일로 물리 선로의 정확한 지터를 확정할 수 없으며 외부 로거나 송신 확인 시각으로 재검증해야 한다. 기록기 헤더의 CAN 500kBit/s만으로 FD/BRS 여부를 판단해서도 안 된다.

**4. 목표각 변화와 실제 추종**

패키지의 각도 슬라이더는 -65~65, resolution=0.1이다. 현재 전달된 목표값은 송신 바이트로 적용되며 ECU의 허용 각도 변화율에 맞춘 램프 제한은 이 설정에 없다.

| 채널 | MCU의 최대 연속 목표각 변화 | USER의 최대 연속 목표각 변화 |
|---|---:|---:|
| BUS1 | 0.375 / 약 10.05ms | 48.5 / 약 9.934ms |
| BUS2 | 0.1875 / 약 10.143ms | 21.875 / 약 9.970ms |

USER BUS1 기록 103.056331→103.066265초에서 -48.5→0, BUS2 125.496558→125.506528초에서 21.875→0이다. 이런 변화는 MCU의 완만한 입력과 다르다. ECU가 변화율 제한/추종 오차 보호를 갖는다면 영향을 줄 수 있지만 사양이나 DTC 없이 보호 작동을 확정할 수 없다.

실제 추종 예:
- BUS1 56.818~77.428초: 목표 22.1875, 구간 끝 피드백 약 22.195로 일치.
- BUS2 74.498~76.368초: 목표 21.6875, 구간 끝 피드백 약 21.795로 근접.

불일치 예:
- BUS1 129.376~131.286초: 목표 12.375 유지, 구간 끝 피드백 약 -0.015. 요청 시작 USER 62395행, 피드백 63368행.
- BUS2 124.197~125.497초: 목표 21.875 유지, 구간 끝 피드백 약 -31.035. 요청 시작 59792행, 피드백 60452행.

0x147의 SYM상 ActiveState는 USER BUS1 14.338871초, BUS2 63.338077초에 1이 되고 이후 기록상 유지된다. 정상 MCU의 활성 전환은 각각 6.305700초, 6.310984초이다. ActiveState 하나만으로 모든 ECU 내부 정상/고장 상태를 판단할 수는 없다.

**5. 패키지 시퀀스와 이전 복사/BUS 질문**

- RUN INIT 자체는 BUS1/2/3의 0x163을 STOP하는 세 단계다. RUN만 눌러서는 이 패키지의 부팅 CMD/RCV가 실행되지 않는다.
- 별도 도구 `BUS1_INIT`, `BUS2_INIT`, `BUS3_INIT`에 4개 CMD/RCV와 DEL, 끝의 0x163 START 및 Enable=1 CMD가 있다. 일반 시퀀스 도구의 RCV이며 RUN INIT 등록 제한과 충돌하지 않는다.
- 세 도구의 CMD `packet_id`, RCV BUS 및 START 대상은 해당 BUS의 등록 패킷과 모두 일치했다. 제공된 corrected 패키지에서 다른 BUS를 잘못 참조하는 문제는 발견하지 않았다.
- 도구 복제는 시퀀스 단계를 deep copy하므로 데이터는 유지한다. 그러나 도구 상위 CAN BUS만 바꾸는 것은 내부 CMD의 등록 packet_id, RCV BUS, START/STOP 대상 전체를 자동 재연결하는 동작이 아니다. 다른 채널용 복제본은 각 단계 참조를 확인해야 한다. 이 패키지는 그 연결이 맞춰져 있다.
- 현재 순서는 START 다음 Enable CMD라 타이머와 이벤트 처리 순서에 따라 Enable=0 프레임이 먼저 송신될 여지가 있다. USER BUS1 첫 0x163은 Enable=0, 같은 기록 시각 다음 프레임부터 1이다. 개선 시 Enable=1 CMD를 준비/송신한 뒤 START하는 순서가 더 명확하다. 이것 하나로 중간 조향 불량을 설명할 수는 없다.
- 이후 주기 TesterPresent는 이 패키지에 없지만, 정상 MCU 로그에도 0x3E 요청은 BUS별 1회뿐이다. 따라서 두 로그 차이의 확정 원인으로 지목할 근거가 없다.
